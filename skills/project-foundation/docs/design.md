# 面向非技术独立开发者的自适应开工基础设施系统设计

日期：2026-09-03
状态：已批准并实现 v0.1.0
项目与 Skill 名称：`project-foundation`

## 1. 背景

Capafy KOL Mission Control 从一个运营工具逐步成长为长期业务基础设施。在持续开发和真实运行中，项目陆续补上了 Git 与 GitHub 治理、版本管理、开发与生产环境隔离、自动测试、数据库 migration 门禁、备份与恢复演练、发布回退、可观测性、供应商费用控制和运维手册。

这些能力不是因为产品功能发生了同等规模的变化才需要，而是因为项目最初没有在写代码前识别生命周期、数据后果、运行方式和长期维护要求。非技术背景的独立开发者通常不知道应该主动询问哪些工程问题，也无法判断某项“最佳实践”是必要保护还是过度工程。AI 编码工具可以快速生成代码，但如果缺少开工边界，会放大隐含假设、环境混用、不可复现构建、无版本发布和事故后无法恢复等问题。

本项目把这些经验泛化为一个面向非技术独立开发者的自适应开工系统。它在第一行产品代码出现前，将业务语言转换成经过确认的项目范围、风险分类、技术路线和最低工程保障，并在项目进入内部试用、正式上线或关键基础设施阶段时提供升级路径。

## 2. 产品定义

`project-foundation` 是一个 Codex 优先、产物尽量工具无关的“开工决策与最低工程保障系统”。它由两部分组成：

1. **Skill**：通过自然语言理解项目、识别风险、推荐技术方案、解释取舍、选择模块并取得用户确认。
2. **轻量基础设施包**：使用确定性脚本和经过验证的适配器生成本地项目起点，并以机械检查证明承诺的基础条件确实存在。

系统不是固定技术栈模板、完整产品孵化平台或企业 DevOps 门户。它的核心工作是：

> 在项目变复杂以前，识别未来最容易后悔、最难逆转和最可能造成事故的决定，并把适合当前阶段的最低保护落到项目中。

## 3. 目标与成功标准

### 3.1 目标

1. 让非技术用户仅用业务语言完成长期项目开工。
2. 在 6–12 个自适应问题内识别项目目标、范围、使用形态、运行形态、风险和维护要求；普通流程目标为 10–20 分钟。
3. 对技术选择给出明确推荐、理由、替代方案和维护成本，由用户以可理解的方式确认。
4. 为所有项目生成通用工程核心，只为真正触发的场景加载增强模块。
5. 对受支持技术栈生成可运行、可测试和可重建的本地起点。
6. 把版本、GitHub、环境、发布、数据、成本、运行和交接要求按项目阶段组织。
7. 让后续 Codex 任务持续读取和执行项目规则，而非仅在初始化时生效。
8. 对“已经生成”“已经验证”“可以开工”等事实提供可重复的机械证据。

### 3.2 成功标准

一个由系统初始化的项目应满足：

- 用户能用一页项目地图说明做什么、为谁做、当前阶段、暂不做什么和下一步是什么。
- 后续 Agent 能识别范围、验收标准、项目规则、技术选择和禁止操作。
- Git、敏感信息、版本和最低验证从第一天存在。
- 受支持适配器能在干净临时目录完成安装、检查、测试和构建。
- 系统不会因技术栈不受支持而伪造成功状态。
- 需要真实用户、长期数据、外部写入或生产运行的项目会自动收到相应环境与恢复建议。
- 项目进入下一阶段时，系统能说明新增风险和必须补充的保护，而不是重建整个项目。
- 用户无需预先学习 Git、CI、staging、migration 或 SLO 才能完成开工。

## 4. 第一版范围

### 4.1 面向对象

第一版首先服务项目所有者本人，作为个人 Alpha 在真实项目中迭代；设计和文件中不写死 Capafy 或个人身份，以便未来公开分发。

第一版只完整支持：

- 从空目录开始的新长期项目；
- 由本系统初始化的项目后续进行开工检查、阶段升级和状态解释。

第一版不承诺对任意既有项目进行完整改造。非空且未由系统初始化的目录应停止生成，并建议未来使用独立的 retrofit/audit 模式。

### 4.2 项目类型

通用入口覆盖：

- 网站和 To C 产品；
- 企业内部多人工具；
- API；
- 自动化和定时任务；
- 数据处理项目；
- Codex Skill。

第一版技术适配器优先覆盖：

1. TypeScript/Node：Web、API、内部工具，包含可选 Cloudflare 部署模块；
2. Python：自动化、数据处理、定时任务和简单 API；
3. Codex Skill：`SKILL.md`、references、scripts、assets 和验证入口。

### 4.3 明确不做

- 不在未经确认时创建 GitHub 仓库、修改仓库权限或 ruleset。
- 不购买服务、创建云资源、写入真实 secret 或部署生产环境。
- 不把市场调研、商业模式、竞品研究和 GTM 设为每次开工的强制流程。
- 不生成 Kubernetes、微服务、复杂容器平台、24 小时值班或大型合规体系作为默认项。
- 不为每个项目强制三套以上远程环境、正式 SLO、SBOM、签名或 SLSA 认证。
- 不用一个固定框架替代项目判断。
- 不在用户确认开工方案前编写产品代码。

## 5. 核心原则

1. **业务语言优先**：询问后果和使用方式，不要求用户选择陌生技术名词。
2. **推荐而非盲选**：系统承担专业判断，给出首选方案、理由和一个必要的替代方案。
3. **风险自适应**：低风险实验偏快；涉及真实用户、付费、敏感数据或长期线上运行时优先可恢复和安全。
4. **单项高风险不平均**：任何一个严重后果维度都可提升风险等级。
5. **阶段性保障**：开工、内部试用、正式上线和关键基础设施使用不同门槛。
6. **最小充分**：每个模块必须说明防止什么问题、为什么现在需要、延后到何时以及维护成本。
7. **判断与事实分离**：AI 负责理解和选择，确定性脚本负责生成与验证事实。
8. **不虚报状态**：明确区分已验证、未验证、不适用和延后。
9. **本地优先、外部显式授权**：第一版安全完成本地开工，外部变更保持后续步骤。
10. **可升级但不静默漂移**：基础包或 Skill 更新不自动重写既有项目。

## 6. 总体架构

系统由四个职责独立的组件组成。

### 6.1 引导与决策 Skill

Skill 的稳定顶层流程为四个阶段：

1. **理解**：提取事实、假设、未知项、用户、问题、成功标准和范围。
2. **决策**：完成项目分类、风险判断、技术推荐、模块选择和用户确认。
3. **生成**：形成内部开工清单并调用编译器。
4. **验证**：运行机械检查，解释结果并给出下一步。

`SKILL.md` 只保存这一决策过程、硬边界和资源路由。项目类型、风险、适配器和详细模块说明放在按需读取的 references 中，避免入口臃肿。

### 6.2 规则与模块库

规则库分为：

- **通用核心**：适用于所有长期项目；
- **项目类型画像**：内部多人、To C、API、自动化/数据、Skill 等；
- **风险增强模块**：数据、身份、支付、外部系统、自动化、生产运行等；
- **技术适配器**：TypeScript/Node、Python、Codex Skill 和可选部署平台。

模块声明触发条件、提供的结果、依赖关系、验证方式、延后条件和维护成本。模块不得只因为它是行业最佳实践就加入。

### 6.3 项目起点编译器

对话确认后，Skill 生成 `.project-start/manifest.json`。它是系统内部唯一事实来源，至少包含：

- schema、Skill、基础包和适配器版本；
- 项目目标、用户、范围和成功标准；
- 项目类型、生命周期、运行形态和风险；
- 已确认技术选择与理由；
- 启用模块及依赖；
- 已知假设、待确认事项及最迟确认阶段；
- 允许和禁止的外部操作；
- 各阶段门槛。

编译器依据 manifest 在临时目录渲染模板，完成本地验证后再写入目标目录。

### 6.4 验证器

验证器只检查已经承诺的基础条件，包括：

- 文件和配置存在且一致；
- 模块依赖完整；
- 无未解释占位符；
- 无疑似 secret 或危险默认值；
- 技术栈最低命令可执行；
- 干净目录可以安装、检查、测试和构建；
- 项目规则与真实配置不冲突；
- 未支持适配器没有被标记为已验证。

结果写入 `.project-start/verification.json`，并映射为“可以开工”“可以开工但有待确认事项”或“暂不可开工”。

## 7. 端到端工作流

### 7.1 接收原始想法

用户自然描述项目。系统先复述理解，并分为：

- 已确定事实；
- 暂时假设；
- 用户必须决定；
- 系统可以代为决定。

### 7.2 自适应澄清

通常询问 6–12 个问题，覆盖：

- 用户与问题；
- 第一版必须完成和明确不做；
- 成功标准；
- 数据保存、丢失和恢复后果；
- 真实用户、付费、敏感信息；
- 外部平台、自动化和写入；
- 使用期限、人数、预算和业务依赖。

一次只问一个会改变方案的问题，允许回答“不知道”。未知项若可能显著提高风险，记录为假设而非按低风险处理。

### 7.3 识别与推荐

系统形成项目画像和工程建议卡，默认显示：

- 项目类型、阶段、生命周期和风险；
- 推荐技术路线、通俗理由和替代方案；
- GitHub、版本、环境、测试、数据和运行建议；
- 预计维护成本；
- 现在、内部试用前、生产前和未来触发的事项；
- 经判断当前不需要的内容。

### 7.4 开工确认

用户确认一张简短开工契约：做什么、为谁做、第一版边界、暂不做什么、采用什么基本路线、哪些假设待验证。确认前不得生成产品代码。

### 7.5 编译与验证

系统生成 manifest、选择模块和适配器、在临时目录编译、执行验证、展示结果，并在通过后一次性写入目标目录。

### 7.6 交付

系统优先展示一页人类可读开工报告，说明当前阶段、已有保护、未完成事项、延后条件和下一步。详细机械输出保存在项目内，需要时展开。

## 8. 项目识别与风险模型

### 8.1 五个识别维度

1. **产品形态**：Web、内部工具、API、自动化、数据或 Skill。
2. **使用者形态**：个人、企业内部多人、企业客户或公众 To C。
3. **运行形态**：仅本地、偶尔运行、定时运行或长期在线。
4. **协作形态**：单人、AI 协作、多人开发或公司治理。
5. **后果与风险**：数据、权限、费用、外部系统、自动化和业务依赖。

### 8.2 风险维度

系统检查：

- 数据丢失、重复或错误写入；
- 真实用户和权限；
- 资金或自动费用；
- 隐私和敏感信息；
- 第三方依赖与外部写入；
- 定时、批量、删除和发送等自动化后果；
- 服务中断对业务的影响。

### 8.3 风险等级

- **轻量实验**：本地、合成数据、无真实用户、无外部写入，目标是尽快验证。
- **标准长期项目**：长期维护，可能存在数据库、外部 API 或少量真实用户，要求可测试、可追踪、可恢复。
- **关键生产系统**：敏感数据、资金、不可逆自动化或核心运营依赖，要求先保证数据和恢复能力再上线。

### 8.4 阶段升级

项目阶段为：

`想法验证 -> 本地原型 -> 私人/内部试用 -> 正式运行 -> 关键基础设施`

进入新阶段时重新评估画像，只生成差异：新增风险、必须补充的模块、仍有效的决定和晋级门槛。

## 9. 四个生命周期能力

所有模块按同一抽象层级组织，避免形成平铺清单。

### 9.1 定义

- 用户、问题、使用场景；
- 首期范围和明确不做；
- 成功与验收标准；
- 项目、数据和风险分类；
- 难以逆转的重要决定；
- 待验证假设和重新评估触发器。

### 9.2 建立

- 技术路线；
- 可复现开发环境；
- 工具链和依赖锁定；
- 配置与 secret 边界；
- 源代码和测试结构；
- 最低检查和“完成”定义；
- Agent 工作规则。

### 9.3 交付

- Git 与 GitHub 协作；
- 版本、Changelog、tag 和 Release；
- 开发、测试、预发布和生产环境；
- CI、发布验证、部署和回退；
- 数据 migration 和发布兼容；
- 构建产物与源代码追溯。

### 9.4 运行

- 健康、日志、指标和异常发现；
- 数据备份、恢复与演练；
- 外部 API、费用、配额、容量和降级；
- 故障响应与回归防护；
- 权限、隐私和数据生命周期；
- 项目交接、冻结、关闭和数据处置。

## 10. 通用工程基线

### 10.1 可复现环境

- 固定运行时和包管理工具的支持版本；
- 完整声明和锁定依赖；
- 单一安装、检查、测试和构建入口；
- 只提交配置名称和安全示例，不提交真实 secret；
- 从只有 tracked 文件的干净目录完成重建验证；
- 不依赖开发者电脑上的隐形业务文件。

### 10.2 测试与完成定义

按项目触发逻辑、集成、浏览器流程、供应商契约、migration 和发布 smoke 等测试。每项变更至少满足验收、最低测试、错误状态、文档/版本同步和无秘密/临时调试内容。

### 10.3 依赖与供应链

- 新依赖说明用途和维护状态；
- 提交 lockfile；
- 检查漏洞和许可证；
- 定期更新并删除无用依赖；
- 关键或公开发布项目增强为 SBOM、构建来源和签名，但不作为所有项目默认要求。

### 10.4 数据生命周期

记录收集目的、来源、存储、访问、保留、日志、备份、测试使用、导出、更正、删除和项目关闭后的处置。真实数据不得无提示进入非生产环境。

### 10.5 生产就绪

区分“代码完成”和“允许生产运行”。生产前需按项目验证健康、依赖、异常发现、负载、成本、备份、回退、发布后 smoke 和责任入口。

### 10.6 备份与恢复

存在重要持久数据时，定义对象、频率、保留、加密、恢复凭据、隔离验证和最近演练。代码回退与数据恢复始终作为两种不同操作。

### 10.7 成本、容量与降级

记录月度预算、免费额度和硬上限、昂贵操作、增长曲线、告警/检查点、停止开关、降级顺序和必须保留的核心能力。

### 10.8 重要决定记录

使用轻量 ADR，仅记录影响系统结构、重要质量属性、长期成本或难以逆转的选择。每条包含背景、选择、替代方案、理由、后果和重新评估条件。

### 10.9 连续性与退出

记录仓库、平台、域名、secret、备份和恢复入口；说明唯一维护者不可用时如何接手；定义冻结或关闭项目时的定时任务、费用、用户通知、数据导出/删除和凭据撤销。

## 11. GitHub、版本与环境工作流

### 11.1 GitHub

个人长期项目默认：

- 选择仓库可见性；
- `main` 保存稳定版本；
- 短期分支承载独立变更；
- Pull Request 汇总目的、影响和验证；
- 自动检查后合并；
- Issue/任务与变更关联；
- secret 和生成物不进入仓库。

多人协作按需增加 ruleset、必需检查、PR 模板、责任区域、权限和禁止 force push。系统必须识别 GitHub 套餐限制并给出真实替代方案，不声称未生效的保护已经存在。

### 11.2 版本

长期交付产品默认使用 SemVer、`CHANGELOG.md`、Git tag 和 GitHub Release；内部任务可按用途选择业务版本与构建编号。系统保证：

- 当前版本事实来源唯一；
- package/manifest/changelog 一致；
- 正式版本可追溯到 commit 和构建；
- 发布说明面向人而非只罗列 commit；
- 已发布版本记录不静默重写；
- 回退目标可识别。

### 11.3 环境

系统区分本地开发、自动测试、预发布和生产。不是所有项目都需四套环境；出现真实用户、长期数据、外部写入、定时任务、业务中断风险、按量收费依赖或数据结构演化时，默认建议至少隔离非生产与生产。

隔离意味着数据库、secret、供应商额度和写入目标均不共用。生产只接收已经验证的同一 commit/构建，不能从开发机未提交状态重新构建。

默认变更路径：

`明确变更 -> 短期分支 -> 本地验证 -> GitHub 自动检查 -> 预发布验证 -> 人工确认 -> 生产发布 -> 发布后检查 -> 记录版本`

## 12. 项目类型画像

### 12.1 企业内部多人系统

默认评估权限矩阵、管理员能力、操作审计、数据导入/导出/修正、员工加入/离开、多用户冲突、备份恢复、系统状态、关键操作确认和接手路径。

### 12.2 To C 产品

默认评估注册登录、账户恢复、隐私和删除、滥用和限流、浏览器/设备、性能峰值、错误提示、分析与同意、客服反馈、灰度/回退和第三方登录/支付/通知失败。

公众 Web 产品按需采用 WCAG 2.2 可测试要求，不把完整标准无差别加载到非 Web 项目。

### 12.3 自动化和数据系统

默认评估幂等、断点续跑、重复写入、来源和时效、外部限额、停止开关、失败记录、重试、人工修正和数据质量。

### 12.4 公共 API

默认评估接口契约、认证、授权、限流、幂等、版本兼容、弃用时间、错误语义和调用方迁移。

### 12.5 AI 产品

默认评估模型/供应商版本、评测集、提示词变更、输出风险、人工复核、成本上限、数据使用、供应商降级和可重复评估。

### 12.6 Codex Skill

默认评估触发边界、渐进披露、instructions/scripts/references/assets 分工、确定性逻辑、真实使用场景、验证和版本兼容。

### 12.7 条件性画像

支付、多租户、公开开源和移动应用作为条件模块；第一版可以给出完整决策与阶段要求，但只在拥有经过验证的适配器时自动生成技术配置。

## 13. 生成产物

通用项目结构为：

```text
START-HERE.md
AGENTS.md
CHANGELOG.md
.gitignore

docs/project/
├─ brief.md
├─ architecture.md
├─ roadmap.md
├─ operations.md          # 按需
├─ release-process.md     # 按需
├─ stage-gates.md
└─ decisions/
   └─ 0001-initial-foundation.md

.project-start/
├─ manifest.json
├─ verification.json
└─ generated-files.json
```

仅在存在秘密配置时生成 `.env.example`。技术适配器再加入源代码、测试、工具链和 GitHub Workflow。没有运行环境的项目不生成运维手册；没有正式发布需求的实验项目只保留简单变更记录。

### 13.1 文件职责

- `START-HERE.md`：面向所有者的一页项目地图；
- `AGENTS.md`：后续 Agent 的项目工作规则；
- `brief.md`：用户、问题、范围、成功标准；
- `architecture.md`：当前结构、边界和关键依赖；
- `roadmap.md`：按阶段而非虚构日期组织的建设路径；
- `stage-gates.md`：开发、内部试用、生产和关键基础设施门槛；
- `decisions/`：重要且难逆转的决定；
- `.project-start/*`：系统内部事实、验证和文件所有权。

## 14. 非技术交互

### 14.1 问题设计

系统询问业务后果。例如不问“是否需要 staging”，而问“新版本出错时，是否可以让真实用户先承受问题”。技术词第一次出现时同时给出业务语言名称。

### 14.2 工程建议卡

识别完成后自动展示项目类型、阶段、生命周期、风险、技术路线、GitHub、版本、环境、最低测试、数据保护、运行保障和推荐理由。用户可以接受、要求解释、查看替代方案、修改业务条件或显式接受暂缓风险。

### 14.3 风险接受

暂不采用某项保护时，记录放弃内容、后果、原因和最迟重新评估阶段。被接受的临时风险不得从报告中消失。

### 14.4 开工报告

报告优先显示：

- 开工状态；
- 做什么和首期范围；
- 已准备的保护；
- 当前明确不做；
- 未验证和延后事项；
- 下一步应给 Codex 的自然语言任务。

“可以开工”只代表当前开发阶段条件满足，不代表产品成功、适合生产或所有未来风险已解决。

## 15. 阶段门

### 15.1 允许开始开发

目标、首期范围、技术选择、项目规则、Git 基线、secret 边界和最低验证存在且一致。

### 15.2 允许内部试用

按项目增加真实身份、隔离测试数据、错误记录、基本恢复、支持入口和内部试用验收。

### 15.3 允许正式上线

按项目增加版本发布、非生产验证、生产配置、数据备份与恢复验证、健康/异常发现、费用边界、回退路径和发布后 smoke。

### 15.4 允许成为关键基础设施

增加恢复演练、权限审计、容量与降级、事故处理、交接和关键访问恢复。

## 16. 安全写入与失败行为

### 16.1 文件安全

- 只对空目录或本系统已初始化目录执行生成；
- 先在临时目录生成并验证；
- 同名文件展示差异，不静默覆盖；
- 失败不留下半成品；
- 不删除用户文件；
- 不写入真实 secret；
- 不执行未经授权的外部操作。

### 16.2 文件所有权

`.project-start/generated-files.json` 为每个生成文件记录模块、生成摘要、当前是否修改、是否允许重生成以及更新策略。文件分为：

- **系统管理**：可安全重生成的机器结果；
- **共同维护**：更新前必须比较的项目地图和 Agent 规则；
- **项目所有**：产品代码和人工决定，系统永不自动覆盖。

### 16.3 失败矩阵

- 答案冲突：指出冲突，只追问改变方案的问题；
- 关键风险未知：允许安全本地工作，阻断依赖风险的阶段；
- 非空未初始化目录：停止生成；
- 工具缺失：给出补充步骤，标记未验证；
- 网络不可用：完成本地部分，外部检查标记未验证；
- GitHub 能力不支持：记录限制和替代保护；
- 技术栈无适配器：生成通用核心，不声称技术配置已验证；
- 测试/构建失败：标记暂不可开工并保留错误；
- 疑似密钥：阻止进入 Git 基线，要求处理。

## 17. 系统自身的版本与更新

系统分别记录 Skill、基础包和适配器版本。项目 manifest 固定自己采用的版本，不因个人 Skill 更新而自动变化。

更新既有初始化项目时先比较：

- 新保护是否适用；
- 文件是否仍为生成状态；
- 用户修改是否会冲突；
- 工作流是否变化；
- 是否需要人工决定。

结果分为“可安全自动更新”“查看差异后更新”和“仅提供迁移说明”。

系统自身使用 SemVer、`CHANGELOG.md`、Git tag、自动测试、干净环境安装、升级说明和不可变已发布记录。重大规则变化必须说明受影响项目；适配器依赖更新必须先通过临时项目验证。

## 18. 测试策略

### 18.1 规则不变量

至少验证：

- 真实用户数据不能归为纯本地低风险实验；
- 生产数据库必须评估备份和恢复；
- 定时外部写入必须有停止和幂等保护；
- 生产发布必须有版本识别和发布后检查；
- 高风险维度不能被其他低风险项平均；
- 不支持适配器不能声称技术验证完成。

不测试 AI 是否输出固定措辞，只测试关键决定和输出契约。

### 18.2 生成器

验证一致输出、冲突保护、事务性、无占位符、模块依赖、文件所有权、幂等和 secret 拦截。

### 18.3 适配器

每个适配器在全新临时目录实际运行初始化、安装、类型/语法检查、测试、构建、GitHub Workflow 基本校验和敏感配置检查。全部通过后才能标记“已验证”。

### 18.4 场景

至少覆盖：

1. 低风险周末原型；
2. 本地 Codex Skill；
3. Python 定时数据自动化；
4. 企业内部多人运营后台；
5. 数据库和外部 API 的长期 Web 应用；
6. 带注册、隐私和支付的 To C 产品；
7. 不支持技术栈；
8. 本地原型升级到内部试用和生产。

## 19. 第一版验收标准

全部满足才算第一版完成：

1. 新用户可用自然语言在 10–20 分钟内完成普通长期项目开工。
2. Skill 在确认方案前不生成产品代码。
3. 通用核心可用于六类项目，不依赖特定部署平台。
4. TypeScript/Node、Python 和 Codex Skill 适配器均通过干净临时目录验证。
5. 生成操作对空目录事务化，对非空未初始化目录安全停止。
6. 项目包含可读地图、Agent 规则、范围、阶段门、决定记录、版本记录和机械验证结果。
7. 真实用户、数据、自动化、外部 API 和生产运行能触发对应模块。
8. GitHub、版本与环境建议会在识别后默认出现，无需用户主动知道这些概念。
9. 所有状态明确区分已验证、未验证、不适用和延后。
10. 文件所有权与版本记录能防止后续更新静默覆盖项目修改。
11. 场景测试证明低风险项目不过度工程，高风险项目不遗漏关键保护。
12. 系统自身具备 SemVer、Changelog、自动测试和升级说明。

## 20. 研究依据与边界

以下资料用于提炼原则，不表示第一版追求完整合规：

- GitHub Spec Kit：规格、计划、任务、实现的意图驱动流程；
- OpenAI Codex Skills 与 `AGENTS.md`：可复用工作流、渐进披露和项目级规则；
- NIST SSDF：安全开发环境、风险/决定记录、发布来源和漏洞响应；
- OWASP SAMM/ASVS：治理、设计、实现、验证、运行及 Web 安全验证；
- OpenSSF OSPS Baseline 与 SLSA：分级的最低要求、依赖和构建来源；
- Twelve-Factor App：依赖、配置、构建/发布/运行和开发/生产接近；
- Google SRE Production Readiness Review：面向具体服务的生产准备；
- NIST Privacy Framework：完整数据处理生命周期；
- W3C WCAG 2.2：公众 Web 产品的可测试无障碍要求；
- AWS Well-Architected：运行、安全、可靠性、性能和成本的系统性权衡；
- Microsoft ADR：重要架构决定的背景、选择、理由和后果记录；
- NIST AI RMF：AI 项目的生命周期风险和评估。

系统只吸收能够改变实际判断、生成或验证的原则。企业框架中的组织治理、合规证明和重型控制不会因为出现在来源中就进入个人项目默认基线。

## 21. 后续而非第一版

- 任意既有项目 retrofit/audit 模式；
- Claude Code、Cursor、Copilot 等完整 Agent 适配；
- 可视化开工向导；
- 更多语言、框架和云平台适配器；
- 团队模板目录和企业策略包；
- 远程 GitHub/云资源的授权自动化；
- 公开插件分发和第三方适配器生态。

这些能力必须在个人 Alpha 通过真实项目验证后再决定，不提前扩大第一版范围。
