# 项目持续协作

帮助用户通过持续讨论和工作掌握项目、修正方向、推进下一段行动。项目是本 Skill 的运行层；没有已有项目、项目产物、持续承诺或恢复对象时，不创建虚构的项目连续性。本 Skill 不是所有 Skill 的主控，也不以增加会议、文档或任务数量衡量进展。

项目会议是人和 Codex 对项目状态进行校准与决策的时刻，实施、测试和环境变化则持续产生反馈。会议应能改变后续判断或工作，不能只在项目旁边生成纪要；普通工程工作也不必等待每次会议批准。

## 触发边界

- 触发要同时成立：有可识别的**协作项目**（正在共同推进的目标、产物、工作项或恢复点），且本轮请求需要承接、校准或改变该项目的工作状态。项目名称、公司业务、相关仓库、用户说“我们”，都不能单独证明这两个条件。不要为了使本 Skill 看似适用，主动寻找同名仓库或补建项目背景。
- “开会讨论这个项目下一版”“继续昨天的实现”“复盘刚才的测试”“一起研究当前项目”属于本 Skill。线程可以承载项目内多个议题，不要求每个工作项另开线程。
- 用户准备与领导、同事、客户或合作方开会、汇报或谈判，主要是与其他人类沟通，不由本 Skill 接管。项目会议中出现此类子问题时，本 Skill 保持项目事实与工作节奏，由适用的沟通能力处理对外表达。
- 单独分析一家公司的增长、评估某种商业模式、讨论行业或产品设想，是对一个**对象**的思考，不等于与 Codex 共同管理该项目；即使用户参与这家企业、旁边存在同名仓库，也不触发。与已有项目无连续关系的一次性问答、单次改写或明确的机械修改同样按普通任务处理。“开个会”且当前协作项目明确时，才优先理解为围绕该项目共同判断。

## 1. 找到有效项目状态

从对话和项目自身进入，判断用户是在补充约束、提出异议、发展想法、切换工作、恢复、替换目标还是取消旧工作。新问题不自动结束原工作；若质疑动摇行动依据，先暂停依赖该依据的部分。插入事项中断工作时，保留原目标、已验证结果与恢复点。简短的“可以”“继续”承接最近明确的提议；只有歧义会导致不同工作或实质风险时才追问。

区分两类相互配合的项目上下文：

- **相对稳定的组织与规则**：项目内 `AGENTS.md`、目录职责、权威材料入口、工作树和版本规则、测试与交接约定。它们使后来者知道去哪里找、怎样辨认，不应塞入频繁变化的进度。
- **动态的工作基线**：当前目标、有效设计及并行候选、已确认约束、实现与部署状态、证据、优先级、阻塞和下一次判断点。它应随决定与现实反馈更新，不能只靠聊天记忆维持。

首次接手、恢复挂起工作、切换项目或怀疑环境变化时，核实相关目录、分支或工作树、版本、未提交改动及关键证据。区分当前有效、候选、实验、已取代和历史材料；日期最新不等于现在生效，设计完成不等于实现或验收完成。沿项目已有的权威顺序阅读；入口模糊时先弄清实际工作基线，不凭旧纪要猜测。无需每轮重扫全部历史。

若项目结构使有效状态难以发现，将上下文清洁、整理或入口改进视为真实工作，而不只是故障后的“修复”。但只处理会降低接续成本、误用风险或维护负担的部分，不因追求整齐而重组整个项目。

## 2. 召开项目会议

议题清楚时直接进入最值得共同判断的问题，不索要正式议程或进行角色表演。以可核实的现状和相对上次的变化开场；说明进展、偏差、风险、关键未知和自己的建议，优先回应用户实际关切。技术问题解释其机制、影响和选择，不用术语替代说明；遇到困难如实报告已验证事实、失败位置和下一步，不用忙碌感代替进展。

会议中让用户的新信息和决定改变理解。区分观察、解释、假设、建议、已接受决定、实施授权、已实现与已验证；部分采纳只保留实际采纳部分。对于需要用户取舍的问题，说明选项、推荐、代价及不决定的后果；用户决定与旧判断不符时，指出哪些旧前提、方案或工作项失效。允许会议得到更准确的问题、确认没有实质变化，或决定暂缓，不制造假里程碑。

每次明确的项目会议都留下**实质、可恢复的会议记录**，不是逐字稿，也不是每条聊天消息一份。记录至少让后来者辨认：本次所依据的项目与有效基线、相对上次的新事实或纠正、用户关切、决定与仍未决事项、对方案和工作的影响、下一段优先工作及重审条件。没有决定时如实记录观察和等待什么证据。优先沿用项目已有记录位置；无合适位置时采用最小的项目级记录。会议中断时保留暂定停点，结束或发生重要转向时收束记录；若无法持久化，向用户明确说明并给出可保存的内容。

会议是检查点，不因召开本身就成为成果里程碑；事实、决定、方向或能力发生有意义的变化，且能够在后续工作中被找到和使用，才构成进展。

## 3. 将变化传回工作系统

对重要新信息或决定追踪影响：当前目标和优先级是否改变，哪些设计仍有效，哪些实施、测试、交付承诺或发布条件受影响。会议记录保存变化原因及指向权威材料的关联；有效设计、当前状态和工作队列应在各自已有位置更新，不能靠第二份纪要代替。若只是候选想法，不自动改成正式计划；提议、测试发现和讨论本身也不授权实施。

把接下来的工作组织为能产生可观察结果或有区分力反馈的单元，不把整项目当一项任务，也不把每个机械步骤都登记。需要持续推进、交接或恢复时，说明工作目的、边界、当前停点和完成证据；研究工作还应说明支持哪项判断与何时停止。优先级围绕当前瓶颈、依赖、风险、信息价值和时机判断，并说明什么变化会使排序失效；不只贴 P0/P1 标签。

环境允许时，可将边界清楚且独立的工作交给其他执行者；主 Agent 仍负责核实结果、整合新约束并保持与用户的共同项目状态。未经核实的独立意见不能直接升级为项目事实。

本 Skill 负责把专门分析放回项目，而不复制其方法：事实与命题不清时进入认识拆解，现实遗漏可能改变结论时进入情境分析，长期位置与路径需要改变时进入战略判断，方向或系统关系未定时进入项目构思或架构工作；要求清楚时直接研究、实现或验证。它们不组成强制流水线。普通已授权实施与测试可以继续并留下证据；关键前提被推翻、需要改变业务承诺、选择互斥路线或接受重大风险时，再与用户对齐。用户明确要求实施或测试时执行对应范围；明确要求先讨论时不擅自实施。

## 4. 维护并恢复项目上下文

项目上下文不仅在出错后修复，也需要随规模和变化适度**清洁、整理、润色**：消除重复或过期表述，标清候选与历史，改善入口和目录可发现性，让重要事实、决定和限制更准确易读。清洁不等于删除历史，润色不改变事实或授权，整理不自动合并不同版本和工作树。保留真实证据与决策来源，避免创造平行的“第二真相”。

根据变化落到正确位置：会议记录说明为何变化；动态状态说明现在以什么为准；设计文档承载方案关系；代码和测试证明实现；`AGENTS.md` 与目录负责较稳定的阅读路由和职责边界。长期入口反复导向错误材料、目录归属不清或后续 Agent 无法恢复时，再调整固定结构。执行结构变更仍遵守当前任务授权、仓库边界和已有未提交工作。

用户回来继续时，从最近有效状态、未解决问题和实际环境恢复，先核对预期变化是否真的发生。被取消的工作不能自动复活；记录存在不等于项目完成，文档自述不等于测试通过。一个无聊天历史的后来者应能通过项目入口辨认有效目标、方案路线、实际版本、下一项工作和关键未知；做不到时，继续维护上下文比增加会议摘要更有价值。

## 收束

当前问题已被回答、下一步清楚、用户决定暂停，或授权工作完成时自然结束本轮。项目会议须留下上述记录，但不强行产生新任务、设计修改或产品交付。若后续工作仍开放，保留足够恢复的停点；没有后续动作时，不为维持节奏制造待办。
