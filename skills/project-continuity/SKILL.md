# 项目承接

让后续工作使用正确的事实和决定，而不是积累协作记录。本 Skill 只负责状态恢复、决定传递和恢复点，不接管技术判断、研究方法、日常执行或资源调度，也不要求创建固定的一组文档。

## 恢复有效状态

首次接手、跨线程交接、中断后恢复，或发现状态冲突时，从项目已有入口核对当前目标、有效决定、实际实现与尚未完成的工作。按本次需要确认目录、工作树、分支、未提交改动和关键证据；状态有效时不重复扫描。历史材料只在追查原因或解决冲突时展开，不用记录数量或更新时间代替事实核对。

区分用户决定、已核实条件、候选方案和模型假设。历史方法不能自动成为当前约束；被取代的方案和被取消的任务不自动恢复。文档写了、代码改了、功能生效和实际交付是不同状态。

线程可以承载多个工作项和讨论，不要求用户切换线程。接续时识别当前请求与原工作的关系；询问不自动取消原工作，讨论不自动授权修改。上下文不足时，先查可获得的事实；只把无法自行解决且会改变行动的歧义交给用户。

## 传递已确认变化

当用户决定或已核实事实改变后续工作时，找到实际受影响的目标、方案、实现要求或状态位置。替换失效的当前内容，保留必要理由与证据位置；不靠不断追加例外让后来者自行裁决。同一事实维护一处，不为一次测试或局部完成同步重写一组文档。

保留决定的目的及其适用边界，而不只摘录字面动作。区分已接受的方向、实施授权和已生效结果：决定可能只改变后续方案；在已授权实施中，则检查受影响的执行安排是否真的采用了它。记录不能代替实现或验证，模型自己提出的下一步不能自动成为用户决定。

普通讨论、解释、逐次测试和运行日志不写入长期指令。只有尚未由现有权威材料承载、且会影响后续工作的变化才需要保存；没有实质变化可在对话中完成。用户明确要求纪要时按其范围提供，不把纪要整体提升为执行约束。

## 保存必要恢复点

工作确实暂停、交接、受阻，或需要跨会话接续时，在已有合适位置留下：原目的与授权边界、已验证结果、尚未解决的问题、继续工作所需的定位或证据。只保留让后来者能继续的内容，不复制整段讨论或另建管理体系。无法持久化时明确说明。

恢复点是接续工具，不是停止理由。已授权工作仍有安全可行的下一步时继续执行；局部测试、PR、子任务或记录完成不代表整个请求完成。讨论结束不强行生成工程任务。

遵守项目的仓库、权限和未提交改动边界；不为整理上下文擅自删除历史、合并工作树或向其他线程发消息。
